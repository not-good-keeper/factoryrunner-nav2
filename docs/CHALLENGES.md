# Challenges

This is the engineering record behind the project. It opens with how the work fitted inside a robot and a navigation stack that could not be changed, then explains the mechanism behind each of the main fixes, and ends with a dated log of the problems themselves, including the ones that turned out to be bugs in this repository's own code.

## Working inside a fixed robot and a fixed stack

The assignment fixes the robot, a stock TurtleBot3 Waffle, and asks for Nav2 rather than a custom navigation algorithm. That is close to how a factory works. A robot arrives built, certified and supported by its vendor, and the software around it has to make do with the sensors and controllers it already has. So "no changes to the robot and no home-grown navigation algorithm" was treated as a hard limit, and most of the interesting work came from finding what was possible inside it.

Computer vision is the clearest example. The Waffle has no RGB camera, and adding one would have meant changing the robot. Before giving up on perception, it was worth reading the robot's own model file (`gz_waffle.sdf.xacro`) and listing what Gazebo was publishing. The Waffle turned out to carry a RealSense depth camera that Gazebo was already rendering at 5 Hz, with nothing subscribed to it, because Nav2's TB3 launch never bridges it into ROS. Bridging that existing sensor in a separate launch file and writing a C++/OpenCV detector on its depth images gave the project perception without touching the robot. It also exposed a real gap: a 10 cm crate that sits below the LiDAR's scan plane, which Nav2 drove straight into.

Machine learning followed the same reasoning. With no images to learn from, the useful data was what the robot already produced, namely lap times, clearances and recoveries, and the useful levers were Nav2 parameters that can be changed while it runs. Bayesian optimisation over four of them, scored by the trial harness and checked on laps the study never saw, put learning where the data is while leaving planning and control entirely to Nav2.

Changing how the robot navigates without writing a navigation algorithm meant leaning on configuration. Costmap filters give the keepout lane and the speed zone, collision-monitor polygons give the safety fields, and the order of costmap plugins and the behaviour tree's timeouts turned out to matter as much as any of them. Everything else, from the mission controller and its leg timeout to the trial harness and the health monitor, sits in an application layer on top of Nav2 and talks to it only through its normal interfaces.

The surrounding platform had its own limits. When Nav2 froze, the debugger could not attach because WSL's `ptrace_scope` setting forbids it, and sudo was reserved for package installs. A parent process is still allowed to trace its own children, so the Nav2 process was started under gdb through `ros2 launch --launch-prefix` instead. GitHub Actions is unavailable on the account because of a billing block, so `scripts/check.sh` runs the same lint, build and test steps locally, on a clean copy of exactly the files git would commit. Moving a pallet across the aisle through the `gz` command-line tool took 0.6 s per step, far too slow, but Gazebo's Python transport bindings ship with ROS Jazzy and answer in about half a millisecond. And the C++ package could not simply sit inside this Python package, because colcon stops searching once it finds one, so it is passed to colcon as a second base path and no existing file had to move.

The common thread is that several of the most useful pieces, among them the depth camera, Nav2's runtime parameters, Gazebo's transport API and colcon's base paths, were already there and unused. Reading what the system provides came before adding anything to it.

## How the main fixes work

**Why the freeze was in Fast DDS rather than AMCL.** The visible symptom pointed at localization, since the `map → odom` transform disappeared. But `ros2 lifecycle get /amcl` answered "Node not found", every Nav2 node had dropped off `ros2 node list`, and the process hosting them was still alive, in one run idle at 0 % CPU. A crash in AMCL would not make every other node vanish with it, so the whole process was the thing to inspect. A dump of its 75 threads showed 20 of them blocked on Fast DDS locks (12 waiting for a send buffer, 7 on a reader mutex in in-process delivery, 1 in discovery cleanup), about 49 executor threads idle waiting for messages that would never come, and no Nav2 code on any blocked path. AMCL was a victim of a stuck middleware rather than the cause. Under Cyclone DDS the freeze has not appeared in any run since, against two freezes in three runs under Fast DDS, which is strong evidence but not a proven Fast DDS bug.

**Why one late reply aborted a whole goal.** Nav2's default behaviour tree replans once a second by sending a `ComputePathToPose` goal to the planner, and it waits `default_server_timeout`, 20 ms in Jazzy, for the planner to acknowledge it. When the acknowledgement arrives later than that, the tree node fails without setting `compute_path_error_code`. Both recovery branches of the tree begin with a condition, `WouldAPlannerRecoveryHelp` or `WouldAControllerRecoveryHelp`, which passes only for a short list of error codes where clearing a costmap or spinning might help. An unset code is not on that list, so the tree skipped every recovery and aborted the goal about 30 ms after the warning. A 200 ms timeout gives the planner room to answer. The broader point is that recovery in this tree is gated on error codes, so any failure that never sets one bypasses recovery altogether.

**Why the keepout filter has to come before inflation.** Costmap plugins run in order and write into one shared grid. The inflation layer finds the lethal cells already in that grid and spreads a decaying cost around them. With the keepout filter listed after inflation, the forklift lane was marked lethal only once inflation had finished, so it had no cost band at all. The planner saw free space right up to the lane's edge and planned along it, and MPPI, which cuts corners, then put the robot's body over the lane's corner, where every candidate trajectory counted as a collision. Listing the filter first gives the lane the same 0.7 m band as a wall. A probe of the live costmap shows the band, and the corner failure, which had appeared in 2 of the 11 runs that reached that corner, has not appeared since.

**How MPPI works, and what the tuned values change.** MPPI (model predictive path integral control) samples 2000 noisy velocity sequences around its previous best plan, rolls each one forward through the robot's motion model for 56 steps of 0.05 s, a 2.8 s horizon, and scores every rollout with a set of critics. It then takes an average of the sequences in which better-scoring ones count for more, with `temperature` (0.3 here) setting how strongly the best dominate, and sends the first velocity of that average. The parameter study adjusted `vx_max`, the forward speed cap; the PathFollow critic's weight, which rewards progress along the global path; and the Cost critic's weight, which penalises rollouts that pass through high cost near obstacles. The fourth parameter, the local costmap's `cost_scaling_factor`, sets how quickly inflation cost falls away from an obstacle and so changes what the Cost critic sees. The tuned set ended up with a slightly lower speed cap than the default and was still 3.5 s faster per lap on the median of ten laps each. Heavier path-following and obstacle-cost weights producing fewer corrections would explain it, though that has not been tested directly.

**Why the robot locked up in the stop field, and how a real robot should handle it.** The collision monitor sits between the velocity smoother and the wheels, and when any scan point falls inside its `StopZone` box it replaces every outgoing command with zero, whichever way the command points. In one of the closest pallet drops the pallet ended up inside that box, so the commands that would have backed the robot out were zeroed as well and nothing could move it. The leg timeout ended the leg after 120 s and logged it as canceled. On a real robot the stop field should depend on the direction of travel. Jazzy's collision monitor supports velocity polygons that change shape with the current command, so backing away from an obstacle in front stays possible. A stop state that lasts more than a few seconds should also raise a call for an operator, and a hardware emergency stop belongs underneath all of it.

**What the TPE sampler does, and why validation used a different spot.** Optuna's tree-structured Parzen estimator begins with ten random trials. Trial 0 was fixed to the default configuration, so trials 1 to 9 were random, which is where most of the poor scores sit. From then on it divides the trials so far into a better and a worse group by score, models how each parameter is distributed in each group, and proposes values that are likely under the better model and unlikely under the worse one. Validating on fresh laps matters for two reasons. With 25 noisy trials the best score is partly luck, because the winning trial is the one whose noise happened to help, so its score flatters it. Re-measuring both configurations on new laps removes that bias. Tuning against one pallet position can also fit that position, and a position the study never used tests whether the gain carries over. Alternating default and tuned laps keeps any slow drift in the simulator from favouring either side.

## Log

### 26 October — Wrong Ubuntu version for Jazzy

The existing WSL environment ran Ubuntu 20.04. ROS 2 Jazzy ships binaries only for Ubuntu 24.04, and Humble on 22.04 still uses Gazebo Classic for the TurtleBot3 simulation, so neither matched the plan. A separate Ubuntu 24.04 distribution was installed next to the old one rather than upgrading it in place, and everything in this repository was built and run there.

### 26 October — Keepout and speed zones that silently did nothing

After the keepout and speed filters were added, both costmaps kept logging `KeepoutFilter: Filter mask was not received`, and planned paths still went straight through the forklift lane. The mask server was publishing (reliable, transient local) and the filter info server was publishing on `/keepout_filter_info`, yet the costmap said it had subscribed to `keepout_filter_info` with no leading slash. That was the clue. The topic names in `nav2_params.yaml` were relative, and because the costmaps run in their own namespaces they were listening on `/global_costmap/keepout_filter_info`, which nothing publishes. The speed filter's `speed_limit` output had the same problem. Once every filter topic was made absolute, both costmaps received their masks, the next path crossed below the lane at about y = −2.8 m, and `/speed_limit` switched to 40 % as the robot entered the CNC zone.

### 26 October — Missions that froze or aborted partway through

The first runs on the development machine finished leg 1 and then stopped. The robot sat still on leg 2 with 9.61 m to go, and `tf2_echo map odom` reported that the `map` frame no longer existed. An earlier run on a cloud machine had failed on the same leg with `Timed out while waiting for action server to acknowledge goal request for compute_path_to_pose`. Localization looked like the obvious suspect.

Reproducing it headless with the committed configuration (Fast DDS 2.14.7 and the default 20 ms server timeout) showed two separate faults. Gazebo ran at a real-time factor of 1.0, so the machine was keeping up. None of three runs completed: two ended with the Nav2 process frozen and one aborted on its first leg.

In the frozen runs, `/scan` still arrived at 4.9 Hz, but the `map` frame was gone, AMCL could not be found, and every Nav2 node had disappeared from the ROS graph while the `component_container_isolated` process that hosts them was still running. The thread dump described above placed the stall inside Fast DDS. Switching to Cyclone DDS is a package install and one environment variable, which the setup script and README now include, and `mission_controller` warns when the variable is missing. Afterwards the freeze did not return in nine runs, nor in any run since.

The other fault survived the middleware change. One run under each middleware aborted a goal about 30 ms after a late planner acknowledgement, which is the error-code gating explained above. Raising `default_server_timeout` to 200 ms ended it, and three consecutive headless missions then completed all four legs in 95.3, 92.0 and 90.7 s of simulated time.

One problem in the test setup surfaced along the way. A `gz sim` server ignored `SIGTERM` and kept its world running underneath the next five launches, so those runs are marked in the table below and not counted. The stop step now escalates to `SIGKILL` and checks that nothing is left before the next launch. One run also failed at the keepout lane's corner before freezing; that turned out to be a separate problem, covered in the next entry.

### 26 October — Stuck on the corner of the keepout lane

Two runs, one under each middleware, stopped on leg 4 with exactly 4.01 m of path left. The controller logged `Optimizer fail to compute path` until it gave up, and the spin recovery quit with `Collision Ahead`. With the robot still stuck, `tf2_echo map base_link` placed it at (2.778, 2.503). The keepout lane spans x 2.0 to 2.8 m and y −2.5 to 2.5 m, so the robot's centre was 3 mm from the lane's corner and its body overlapped lethal cells, from which no trajectory looks safe.

The cause was the plugin order explained above: the keepout filter ran after the inflation layer, so the lane had no inflated margin and the planner hugged its edge. With the filter moved ahead of inflation in both costmaps, a probe of the live costmap read 100 inside the lane, 99 within 0.1 to 0.2 m of its edges, then 78 at 0.3 m, 58 at 0.4 m and 43 at 0.5 m. The old order was never probed, so there is no measured before-and-after. Five missions in a row then finished with no MPPI failures and no recoveries, and the failure has not returned in any run since, against 2 of the 11 earlier runs that reached that corner.

### 27 October — Gazebo replies that confirm nothing

While the obstacle helper was being written, spawning a second box under the same name and removing a box that no longer existed both reported success. `ros_gz_sim create` printed `Entity creation successful.` and exited cleanly, and the world's remove service answered `data: true`. The Gazebo server log told a different story, for example `Entity named [pallet_box] of type [2] not found, so not removed.`, which showed that the reply goes out when the request is queued, before the world has acted on it. Asking the world for its list of entities was not an option either, because the headless server runs without a scene broadcaster, so `gz model --list` timed out and no pose or scene topics exist.

The helper therefore reports a spawn or removal as requested rather than done, and the real check moved to the robot's side. With the box placed 3 m ahead on the robot's path, the global costmap marked it at the expected position, which also confirmed the offset of (−8, 0) between the map and Gazebo's world frame. Every plan after the first two kept about 1 m from the box. Dropping it only 1.2 m ahead made the collision monitor report a slowdown, and the robot passed with about 9 cm to spare.

### 27 October — Perception from a camera the robot already had

The role covers computer vision, but the stock Waffle has no RGB camera and the robot could not be changed. Reading its model file instead of assuming there was nothing to work with showed a RealSense depth sensor (`intel_realsense_r200_depth`, 320 × 240, 60° field of view, 5 Hz, up to 5 m) that Gazebo was already rendering with no subscribers.

`launch/vision.launch.py` bridges the existing depth image and camera info into ROS, and the new C++ package `factoryrunner_vision` turns each frame into obstacles with OpenCV. Two details needed care. The camera's mounting height comes from measurement rather than the model file: floor pixels in live frames put it at 0.226 m, tightly clustered between 0.226 and 0.227, against a first estimate of 0.2. And the node publishes in the image's own frame, `camera_depth_frame`, rather than an assumed one.

The payoff was a blind spot that the LiDAR alone could never reveal. The 2D LiDAR scans a single plane about 0.17 m above the floor, so anything lower is invisible to it and to every costmap it feeds. With a 10 cm crate placed on the path, the camera flagged it 2.83 m ahead, while the closest LiDAR return in the robot's forward sector stayed at 2.47 m, from something behind the crate. The robot drove into it. The detector only observes for now; feeding its detections into the costmaps is the obvious next step, held back because it would change the configuration every other result was measured with.

### 27 October — A C++ package colcon could not find

The detector needed an `ament_cmake` package, while this repository is itself an `ament_python` package, and restructuring working code was not worth the risk. A throwaway workspace with a C++ package nested inside a Python one showed that colcon lists only the outer package: once it finds a package, it stops searching inside it. Passing the nested folder as an extra base path makes colcon find both. The C++ package therefore lives in `factoryrunner_vision/`, and the build command, `scripts/check.sh` and CI all name it with `--base-paths src src/factoryrunner-nav2/factoryrunner_vision`. `rosdep` has the same blind spot, so CI's dependency step names the folder as well. No existing file moved.

### 27 October — The first 10-lap trial stopped after 35 legs

The first 10-lap trial file, `trials_20261026-193027.csv`, ends at lap 9, leg 3, and the trial runner finished with an `ExternalShutdownException` traceback. The navigation was fine, since all 35 completed legs had succeeded. The test script had launched every run under a 15-minute timeout meant for single missions, and ten laps take about 16 minutes. Multi-lap runs now get a longer limit, and the trial runner reports where its finished legs are and exits with code 130 instead of a traceback. The interrupted file stays in `results/`; the complete run is `trials_20261026-194747.csv`, with all 40 legs successful and the pallet dropped on laps 3, 6 and 9.

### 27 October — One tuning trial without its pallet

Trial 16 of the parameter study logged `obstacle spawn failed`, after `ros_gz_sim create` timed out at 30 s, and its CNC_CELL row carries `obstacle=failed`. That lap measured the parameters without the obstacle, so its score of 95.8 is not comparable with the others. It was not the best trial and played no part in validation, and the best trial (23, scoring 88.7) had its pallet, although the sampler did learn from trial 16 and may have been nudged slightly by it. The cause has not been established. The same command spawned the pallet in the other 24 trials and in every earlier run, usually in under a second, and since `ros2 run` starts a fresh Python process and ROS node each time, slow discovery on a busy machine is the likeliest explanation. The trial runner records such failures in the CSV rather than hiding them, which is how this one surfaced. A retry, or spawning through Gazebo's in-process transport as the moving obstacle already does, would make it sturdier.

### 27 October — A ten-second stall takes Nav2 down for good

To test the health monitor, the process hosting all Nav2 nodes was frozen with `SIGSTOP` for 10 s during a mission's first leg and then resumed (`results/freeze_test/`). The monitor warned after 1.3 s that `map → odom` had gone stale, raised an error after 2.3 s when none of the seven watched nodes answered a lifecycle query, and another after 3.3 s as the transform aged further.

After the resume, the stack never came back. Both Nav2 lifecycle managers had gone more than 4 s without a bond heartbeat, and the log shows them declaring `CRITICAL FAILURE ... IS DOWN after not receiving a heartbeat for 4000 ms` and then deactivating and cleaning up every managed node. `bt_navigator` aborted the active goal on the way down, and nothing restarts the stack after such a reset. The monitor briefly returned to OK and then reported errors again about 20 s after the original freeze. The mission controller's leg timeout ended the dead leg after 120 s, and its cancel request gave up after its own 10 s limit, 130 s in total, rather than blocking forever.

So any stall longer than Nav2's 4 s bond timeout, whether from a stuck middleware or an overloaded computer, ends navigation by design. That makes outside monitoring and an application-level timeout necessary rather than optional. A supervisor that calls the lifecycle managers' reset and startup services could restore the stack automatically; it has not been built.

### 27 October — Held still by the stop field

During the obstacle-distance sweep, one of the closest drops ended in a cancellation at the 120 s leg timeout, with 108.6 s spent in the collision monitor's stop state and a closest scan return of 0.32 m (`results/obstacle_sweep_20261026-213234/d1.2/`). The pallet had ended up inside the stop box, where the collision monitor zeroes every command, including the reversing or turning that would free the robot, so neither MPPI nor the recovery behaviours could move it.

The stop box was left as it is. Shrinking it or letting commands through near obstacles would weaken the safety layer this project sets out to demonstrate, and the leg timeout already turns the lock-up into a logged failure rather than a robot waiting indefinitely. A direction-dependent stop field and a call for operator help, both described above, are the better fixes for a real robot. Over two sweep runs the lock-up appeared in none of the 15 laps with the pallet dropped from 1.5 m or further, and in 1 of 5 at the closest setting, where the logged drop distances were 0.91 to 1.17 m.

### 27 October — Two names that broke their base classes

The first run of the health monitor died at once with `AttributeError: 'str' object has no attribute '_executor_event'` inside the rclpy executor. Its lifecycle service clients had been stored in `self._clients`, a name `rclpy.node.Node` already uses for its own list of clients, so the executor iterated over node names instead of client objects. Renaming the attribute fixed it, and running the node against the live simulation before committing is what caught it.

The first moving-obstacle trial crashed after one leg in the same way, with `TypeError: 'Event' object is not callable` raised from `Thread.join()`, and the row for the leg it had just finished was lost (`results/crossing/trials_20261026-212629.csv` holds only leg 1). The mover thread kept its stop flag in `self._stop`, which replaced a private method that `threading.Thread` calls during `join()`. The flag was renamed, a regression test now stops and joins a mover, and the three laps were rerun in `trials_20261026-215920.csv` with all 12 legs successful. In both cases a private name collided with a framework base class, and neither showed up in unit tests of the pure logic. Running the real thing caught both.

### 27 October — Background processes that would not stop

Three times in one night a process ignored a clean stop. A `ros2 bag record` started in the background kept recording after `pkill -INT` and never wrote its metadata. The first Docker run completed its mission, all four legs in 91.9 s, but the container never exited until an outer 20-minute timeout killed it. And earlier, a `gz sim` server ignored `SIGTERM` and kept its world running underneath later launches.

The first two share a cause. Bash starts background jobs of a non-interactive shell with `SIGINT` ignored, and both the recorder and the Docker entrypoint's `ros2 launch` were such jobs, so `SIGINT` did nothing and the entrypoint's exit trap then waited for the launch indefinitely. `docker top` on a detached container gave it away: the mission process was gone and the whole simulation was still running. Background ROS processes are now stopped with `SIGTERM`, which both `ros2 launch` and `ros2 bag` handle, and nothing waits without a limit. The entrypoint sends `SIGTERM`, allows 15 s and exits with the program's status, and as the container's first process it takes anything left over down with it. The local stop script escalates to `SIGKILL` and confirms that nothing remains, which covers the stubborn Gazebo server.
